# HNPC guard poses and ambient animation

Evidence question: why do native human NPCs use player weapon poses and omit
their table-authored ambient actions? Primary authority is Retrobution 20260821.
The native consumer is `network_world_runtime` and the shared player rig.

`NpcAnimation.SetModel` selects the HNPC's `m_iMesh` row from NPC mesh table 2.
`SetHNpcStandMotion` interprets its three male string slots as animation names,
with random thresholds 34 and 67. If an alternate repeats the current clip,
slot zero wins. A missing named clip falls back to `stand1`. Without a table,
`SetStandMotion` uses stand1/2/3/4 at thresholds 40/70/90 and avoids repeating
an alternate. Equipment does not prefix this ambient animation selection.
`EndAnimation` selects the next idle at the animation's authored `end` event;
the transition duration is 0.3 seconds. Movement/combat/death retain priority.

Two independent native omissions were found:

- HNPC visual definitions dropped the three idle slots and always selected
  stand1 or an equipped player's stand variant.
- Shared skeleton GLBs lacked 16 ambient clips per gender, including guard
  poses, conversational actions, and alternate stands.

The Rust command `fusionforge repair-native hnpc-clips` resolves clips
through each primary Animation component's exact pointer array, exports strict
object evidence from CharacterSelection.resourceFile, and calls
`export_player_rig_clip_additions` using the existing native coordinate and curve
decoder. It appends accessors, buffer views and animations to the existing GLBs;
all previous animation metadata, indices and binary payload are preserved.
No shared textures, meshes, equipment or existing player emotes are replaced.
Native outputs consist only of the two skeleton GLBs. Provenance stays here.

The native runtime reads `end` events from those GLBs once when opening the HNPC
catalog and shares the small timing maps between instances. Encoded and parsed
staging data are released. Idle playback yields at the authored event rather
than waiting for the last key (rifleguard: 5.0833335 versus 5.3333297 seconds).
Idle requests wait for their own applied revision, recover missing clips through
stand1, and restart even when the next chosen name is unchanged. A replaced rig
does not inherit the old rig's applied animation state.

## HNPC emote sound follow-up

The modular HNPC route originally consumed the recovered animation keys but
never forwarded their `sound` events to gameplay audio. The generic world-NPC
collector only queries its own single-model visual component. Native HNPCs now
read the existing skeleton event payloads once with the catalog and dispatch
crossed events from the applied rig animation revision. Restarting the same
clip starts a new event cursor; skipped distant events are not replayed later.

Primary managed evidence remains in the existing ignored project reports:
`avatar-animation-primary/decompiled/NpcAnimation.cs:308` (`IsStand`) and
`nano-summon-primary/decompiled/AnimationEventHandler.cs:515` (`PlaySound`).
The ambient-state ten-unit gate applies to emotes as well as standing; payloads
containing `_SFX_Dance` bypass that gate and retain ordinary SoundUtil admission.
The native implementation uses the existing semantic gameplay-audio queue,
including localized voice resolution and spatial playback. No new audio payload
or changed publication receipt is required. The published talk, talkexclamation
and talkquestion clips have no sound events; applause, cheer and dance clips do.

Follow-up verification: `cargo test -p ffone-client --lib hnpc_
--no-default-features` passed all seven tests. The same fresh Cargo test
executable passed `player_emote_sounds_resolve_and_spawn_in_both_voice_languages`.
A separately built full client completed the offline crowd fixture at native
position `[-1787, -63.61, 2393]`; its log records male and female applause and
random happy voice events, including repeated emotes, with no schedule panic.
Logs and the verification executable are under ignored
`FFOneClient/target/performance/hnpc-audio`. This establishes event dispatch and
localized audio creation; no microphone/loopback recording was made.

## Same-emote timing correction

The cinema crowd report exposed an error in the initial runtime contract above:
reselecting the same ambient animation must not forcibly restart it at `end`.
`NpcAnimation.MakeUperLayer` sets ordinary clips to WrapMode.Loop; the HNPC
selection uses `Animation.CrossFade`, including when the name remains unchanged.
The native Once/replay path instead discarded the quarter-second tail between
the authored end event and clip length on every same-name selection. For male
applaud these times are 2.01666665 and 2.26666594 seconds; for cheer they are
1.28333342 and 1.53333318 seconds. No extra arbitrary cooldown is established by
the primary managed code.

Native ambient playback now loops. An end-event cursor tracks applied revision,
seek time and loop completions, so the selection is evaluated on event crossings
only. A same-name selection preserves the active request and its time; a
different selection still crossfades at the authored event. Audio continues to
follow actual clip crossings, including natural wraps. Missing event metadata
uses a completed cycle, never an empty player's `all_finished()` result.

Authority was rechecked against the primary raw `main.unity3d` and extracted
assembly hashes recorded above. The exact decompiled `NpcAnimation.cs` has
SHA-256 `627fbb5eb9b87d5973c7927a02b26dd25531e6cb48600dd3698608822cc2e408`;
relevant methods are MakeUperLayer, PlayCrossFade, SetHNpcStandMotion and
EndAnimation. No binary payload changed.

Verification for the correction: all seven HNPC tests passed, including the
new applied-clip tail/cursor regression, followed by the production EN/RU
emote-audio test. The actual client main and library were built with an isolated
foundation artifact under `target/performance/hnpc-timing`; the redundant Cargo
test waiting on the shared build lock was cancelled after these tests passed.
The complete offline runtime fixture at `[-1787, -63.61, 2393]` exited successfully
and wrote its report. Its sound trace proves natural wraps: NPC 2886 retained
revision 12 for completions 0/1/2; NPC 2885 retained revision 85 through
completion 3. Both male and female applause retained their voice events.
Logs, tests and summarized loop counters are under the same ignored directory.
The window screenshot is only 1x1 and is not accepted as visual evidence;
acceptance here is the deterministic simulation trace and ECS regression.
No frame-rate improvement is claimed from this unoptimized diagnostic build.

### Owner-requested parity recheck

Rechecked raw primary main.unity3d and extracted Assembly-CSharp.dll hashes
against the exact-entry receipt; both match the identities above. The same-name
CrossFade conclusion is also supported by Unity's contemporary 3.5.3 manual:
https://docs.unity3d.com/353/Documentation/Manual/AnimationScripting.html
Its Animation Blending example sets Loop and calls CrossFade on the same idle
or walk animation every Update, while describing continuous playback. The API
example does the same:
https://docs.unity3d.com/353/Documentation/ScriptReference/Animation.CrossFade.html
This supports preserving playback time on same-name selection; it is distinct
from Animator/Mecanim APIs and from a forced replay.

Scope of confirmation: managed ambient selection, looping, absence of an added
cooldown, authored end-event timing and 0.3-second transitions. A different clip
still starts its transition at `end`, before the outgoing clip's last key;
only same-name selection preserves the full natural loop. No synchronized
Unity-versus-Bevy frame capture was made, so this is not a claim of pixel-exact
blend curves or identical random sequences in two running clients.
